# Domain Boundaries

Each bounded context is a Go package tree under `internal/`. Packages expose
a small service API; other modules call that API, never each other's
tables. Cross-module reads for reporting go through explicit query functions
or read models, not ad-hoc joins in handlers.

| Module | Package | Owns (tables) | Responsibilities | Must not |
|--------|---------|---------------|------------------|----------|
| Merchant | `internal/merchant` | merchants, applications, api_keys, team members | Onboarding state, live-enablement approval, credentials lifecycle | Decide payment outcomes |
| Payments | `internal/payments` | payments, payment_transitions | Payment resource, state machine, public lifecycle | Call providers directly |
| Orchestration | `internal/orchestration` | routing_rules, routing_decisions | Choose provider for an attempt; failover only when safe | Retry an attempt whose outcome is unknown |
| Providers | `internal/providers/...` | payment_attempts, provider_callbacks | Adapter interface, capability model, one sub-package per provider | Contain business rules about merchants or fees |
| Ledger | `internal/ledger` | ledger_accounts, journal_entries, journal_lines | Double-entry posting, balances derived from lines | Allow updates/deletes of posted entries |
| Refunds | `internal/refunds` | refunds, refund_attempts | Refund lifecycle bounded by refundable amount and capabilities | Share the payment state machine |
| Payouts | `internal/payouts` | payouts, payout_attempts | Payout lifecycle, approvals, limits | Run without explicit authorization |
| Settlement | `internal/settlement` | settlements, settlement_items | Expected vs. actual settlement | Infer settlement from payment success |
| Reconciliation | `internal/reconciliation` | recon_runs, recon_exceptions, imported statements | Match external records to internal ones, classify exceptions | Mutate financial records to force agreement |
| Webhooks | `internal/webhooks` | webhook_endpoints, webhook_deliveries | Signed merchant notifications, retries, dead-letter | Block the payment path |
| Outbox | `internal/outbox` | outbox_events | Transactional event recording and relay | Be the only record of a state change |
| Risk | `internal/risk` | risk_rules, risk_decisions | Deterministic, explainable rule evaluation | Use ML (until justified) |
| Audit | `internal/audit` | audit_log (append-only) | Who did what, when, from where | Be writable by application roles beyond INSERT |
| Reporting | `internal/reporting` | read models / views | Operational (provisional) vs. financial (reconciled) reports | Present provisional figures as reconciled |
| Platform | `internal/platform/...` | — | config, logging, HTTP middleware, DB pool, money, IDs | Contain domain logic |

## Dependency direction

```
handlers (cmd/api, internal/httpapi)
   │
   ▼
payments ──▶ orchestration ──▶ providers (interface)
   │                               ▲
   ├──▶ ledger                      │ implemented by
   ├──▶ outbox                 providers/mpesa, providers/testprovider
   └──▶ risk
refunds, payouts ──▶ ledger, outbox, providers
reconciliation, settlement ──▶ ledger (read + explicit adjustments)
everything ──▶ platform, audit
```

Rules:

- `platform` imports no domain package.
- Provider sub-packages import only `providers` (the interface) and
  `platform`. They never import `payments` or `ledger`.
- Cyclic imports are a design error, not something to work around with
  interfaces declared in the wrong place.

## Transaction boundaries

A single PostgreSQL transaction may span several modules' tables **only**
when the change must be atomic (e.g. payment transition + ledger posting +
outbox event). Modules accept a `pgx.Tx` (via a narrow `DBTX` interface
generated by sqlc) for this purpose; the caller that owns the use case owns
the transaction. Network calls to providers never happen inside a
transaction.
